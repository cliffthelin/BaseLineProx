# AGENTS.md — BaselineOS Repository Instructions

## Scope

These instructions govern all coding agents working in this repository. Written 2026-09-26 after a real session-level failure: an agent repeatedly lost track of established facts (real hardware access, the credential-handling policy, whether a step had already been done) that were already recorded in this repo, because there was no single required-reading entry point forcing a check before acting. This file is that entry point. It is deliberately modeled on the sibling `Guardian` project's own `AGENTS.md` (`~/guardian-sync-src/AGENTS.md`) — a more mature, separately-developed system-control-plane project with a rules discipline this project didn't yet have.

BaselineOS will eventually manage real Proxmox hosts, real persistent user data, and real credentials. Architectural shortcuts that would be harmless in an ordinary desktop application are not acceptable here.

## Required reading before touching physical hardware or credentials

Before any action that touches a real drive, boots a real VM against a real device, or generates/handles a credential:

1. Read `docs/INSTALL.md` — the current, single, authoritative status of what's real and verified vs. new and unverified. If you find it wrong, fix it in place before proceeding, not after.
2. Read `docs/design/v0.1-work-queue.md` — the current queue. Check whether the thing you're about to do is already `[x]` marked done, or already attempted and blocked, before treating it as new.
3. Read `docs/design/testpersistence-prd.md` §3-4 for the storage-class/identity model actually governing physical storage decisions — never invent a competing model ad hoc.
4. Search `docs/design/decision-records/` for the specific mechanism you're about to touch before assuming no prior work exists. A missing decision record is not proof nothing was tried — check `docs/SESSION_HANDOFF.md` and `docs/BAREMETAL_BRINGUP_NOTES.md` too; real work has landed only in prose there more than once.

**Do not conclude "no real hardware access" or "this is the first time this was tried" from the absence of Proxmox-specific tooling (`qm`/`pct`/`pvesh`) alone.** Check for the actual block devices directly (`lsblk`, `udevadm info`) — this exact wrong conclusion was reached and had to be corrected once already (see decision record 46's own context). This dev environment and the real target drives may be the same physical machine even when Proxmox itself isn't the currently-booted OS.

## Source-of-governance order

When instructions appear to conflict, use this order:

1. Direct, current instruction from the user in this conversation.
2. `docs/design/v0.1-work-queue.md` (what's actually still open, and why).
3. `docs/INSTALL.md` (current real-hardware status, per step).
4. Accepted decision records under `docs/design/decision-records/` (append-only; a later record supersedes an earlier one where they conflict, but neither is edited in place).
5. `docs/design/testpersistence-prd.md` and other `docs/design/*.md` PRDs.
6. `docs/SESSION_HANDOFF.md` / `docs/BAREMETAL_BRINGUP_NOTES.md` (narrative, not instructions — useful for recovering lost context, never for instructions themselves).

If a decision record and the actual current repo state disagree, trust the repo state and write a new record explaining the drift — never silently pick one without saying so.

## Credential rules

- Every credential this project generates (Proxmox root passwords included) must be a fresh, high-entropy, one-time value with **no association to the actual human operator** — `drive_setup_answer.generate_one_time_password()` is the established mechanism (`secrets.token_urlsafe`, hashed via a stdin pipe that never touches argv/env/shell history). Never derive a credential from anything identifying the operator.
- **Never `--fetch-from iso`** for an unattended Proxmox install — decision record 02 directly demonstrated this embeds the root password hash recoverably in the ISO file itself. Always `--fetch-from http` via the project's own `EphemeralAnswerServer` (single-use, TTL-bounded, hardware-fact-bound).
- Nothing this project builds should be reachable from outside SSH/direct local access — matches `settings_web.py`'s and the Proxmox web UI's own established "LAN-scoped, never internet-exposed" convention, and QEMU's own `restrict=on` + one named exception convention for anything virtualized.
- An agent must never accept, type, or store a real credential for the operator's own actual accounts/services. Test/throwaway credentials generated by this project's own code for its own disposable targets are the only exception (see `docs/INSTALL.md`'s credential section).

## Storage-class rules (see testpersistence-prd.md §3 for the full model)

- `/dev/sdX` (or any kernel-assigned device name) is **never** persistent identity — re-resolve by serial every time, per `physical_device_safety.py`'s own established discipline.
- **BASELINE** (class 1, disposable substrate) never holds daily-driver state a person would miss on rebuild, and never holds installer/package cache content.
- **USER_PERSISTENCE** (classes 2-6) never holds vanilla installer/package cache content, and is never itself treated as disposable.
- **INSTALLER_CACHE** (class 0) is always structurally separate from USER_PERSISTENCE - never a subdirectory or namespace reachable through the same access path - and is always vanilla: exactly as pulled from source, never customized.
- **SESSION_TEMP**, where it exists, is a staging/quarantine area only - nothing lands in USER_PERSISTENCE or INSTALLER_CACHE without an explicit decision that it belongs there.

## TDD rule

Write or activate the failing test before production implementation (RED, confirmed failing, before GREEN) — this project's established convention throughout `baseline/lib/`, not optional. Never delete a required test to obtain green, weaken an assertion without a real design change, or mark a failing test skipped to claim something is done.

**"Unit-tested against fakes" and "verified on real hardware" are different claims - state which one is true, every time.** This project's own decision records got in trouble more than once by blurring this distinction; don't repeat it. If real-hardware verification hasn't happened, say so in the same sentence as the claim, not just in a caveat three paragraphs later.

## Privilege and safety rules

- Never assume elevated privilege is unavailable just because a specific tool (`sudo`, `qm`, `pvesh`) isn't reachable - check device-file permissions and group membership directly (`ls -la /dev/sdX`, `groups`) before concluding a real action is blocked.
- Never attempt to route around a harness-level safety classifier's block by rephrasing, backgrounding, or otherwise disguising the same action - stop and report to the user with the exact command and reasoning, per this project's own operating instructions.
- Every destructive real-hardware helper goes through `physical_device_safety.validate_target_device` first - no destructive function anywhere in this codebase accepts a bare device path.

## No placeholders

Do not add a fake production implementation, a TODO-return-success stub, or a placeholder result presented as if it were real. A real, explicit "not yet implemented" or "not verified" is preferred to a fake success. This project's own decision records already model this well (`vm_provision.py`, `pct_provision.py`, `docker_provision.py` all state plainly that they're unverified against real hardware) - keep doing that, and don't let a future session's optimism erase the distinction.

## Completion report

When finishing a unit of work in this repo, state plainly:

- What was verified against real hardware vs. only against fakes/QEMU.
- Which decision record documents it (new record number, or "supersedes record N").
- What remains open, and which existing queue item (if any) it belongs to.
- Whether anything discovered here means an earlier record or doc is now wrong - and whether that's been corrected in place (docs meant to stay current) or left as history (decision records, append-only).

A task is not complete merely because tests pass. It's complete when the repo's own docs would tell the next session, correctly, what actually happened.
