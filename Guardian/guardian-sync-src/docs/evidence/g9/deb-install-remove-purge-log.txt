G9 real .deb build/install/remove/purge evidence
==================================================

1. Real build via dpkg-buildpackage -us -uc -b (-d only to skip the
   apt-tracked build-dep check, since cargo/rustc were installed via
   rustup rather than apt on this VM -- the toolchain itself is real
   and present, dpkg-checkbuilddeps just can't see rustup installs).
   Produced guardian_0.1.0-1_amd64.deb.

2. dpkg -c confirmed: two real systemd units at
   /usr/lib/systemd/system/{guardian-daemon,guardian-helper}.service,
   D-Bus policy at /usr/share/dbus-1/system.d/, polkit policy at
   /usr/share/polkit-1/actions/, autostart .desktop at
   /etc/xdg/autostart/, six binaries at /usr/bin/. CONFIRMED: no
   .rules file anywhere in the package listing (ADR-008 hard
   constraint).

   First build attempt actually omitted both systemd units silently
   -- dh_installsystemd's single-package auto-detection does not match
   bare debian/<unit>.service filenames the way assumed; fixed by
   calling dh_installsystemd --name=guardian-daemon and
   --name=guardian-helper explicitly in debian/rules. Re-verified via
   dpkg -c after the fix.

   Also caught during first dpkg -i attempt: debian/control's Depends
   listed policykit-1, which does not exist as an installable package
   on Ubuntu 26.04 (renamed to polkitd/pkexec) -- fixed to
   `polkitd | policykit-1`.

3. sudo dpkg -i guardian_0.1.0-1_amd64.deb: succeeded. postinst
   created the guardiand system user (adduser --system --group
   --no-create-home --home /var/lib/guardian/daemon) and both state
   directories with correct ownership (guardiand:guardiand and
   root:root respectively).

4. Started the real installed units (systemctl start guardian-daemon
   guardian-helper): both active; guardian CLI against the real
   installed daemon returned live capability data identical in kind
   to the earlier manually-installed-binary test.

5. sudo dpkg -r guardian (remove, not purge): binaries and units
   removed; /var/lib/guardian/{daemon,helper} and the guardiand user
   PRESERVED. Matches ADR-008 Decision 6's remove semantics exactly.

   Minor note: after the daemon ran once, its StateDirectory=
   systemd directive left /var/lib/guardian/daemon at mode 0755
   rather than postinst's original 0750 -- ownership is still
   correctly guardiand:guardiand, so this is not a privilege-boundary
   issue, but StateDirectoryMode=0750 should be added to the unit if
   the exact mode matters going forward.

6. sudo dpkg -P guardian (purge): /var/lib/guardian/{daemon,helper}
   and the guardiand user were both removed (getent passwd guardiand
   exits 2, dirs return ENOENT). Matches ADR-008 Decision 6's purge
   semantics exactly.

7. REPAIR: a separate, genuinely independent G9 packaging/privilege
   review (post-dating steps 1-6 above) discovered a real gap step 5
   did not catch: /etc/xdg/autostart/guardian-indicator.desktop
   SURVIVED `sudo dpkg -r guardian`, contradicting ADR-008 Decision 6's
   explicit text that remove should delete the autostart entry
   alongside binaries/units/policy. Root cause, confirmed directly:
   debhelper's dh_installdeb unconditionally scans every regular file
   staged under debian/guardian/etc/ at build time and lists it in the
   package's DEBIAN/conffiles metadata; dpkg then treats any conffile
   as administrator configuration and preserves it on remove
   (deleting only on purge). This debhelper version has no
   `--no-guess`/equivalent flag to opt a specific file out of that
   auto-detection.

   Repair: the package no longer stages the .desktop file under /etc/
   at build time at all. debian/guardian.install now installs it to a
   normal, non-/etc vendor path
   (/usr/share/guardian/xdg-autostart/guardian-indicator.desktop).
   debian/postinst's `configure` case copies it into the real,
   standard XDG vendor-autostart location
   (/etc/xdg/autostart/guardian-indicator.desktop) at install time;
   debian/postrm deletes it explicitly on both `remove` and `purge`.
   Because the file is never present in debian/guardian/etc/ during
   the build, dh_installdeb never sees it and never adds it to
   conffiles -- confirmed directly: the rebuilt .deb's control archive
   (dpkg-deb -e) contains no `conffiles` file at all, and
   `dpkg-query -W -f='${Conffiles}\n' guardian` after a real install
   returns empty.

   The FINAL, RUNTIME-INSTALLED path is unchanged --
   /etc/xdg/autostart/guardian-indicator.desktop, the standard XDG
   vendor-autostart location session managers actually scan -- only
   the packaging-internal staging mechanism changed. ADR-008 itself
   was not amended; this repair makes the package actually satisfy
   ADR-008's existing text rather than documenting a deviation from
   it.

   Fresh evidence gathered against the rebuilt .deb, real commands,
   real output (see the packaging-repair completion report for the
   full transcript):
   - dpkg-deb -e control extract: no `conffiles` file present at all.
   - Real install: /etc/xdg/autostart/guardian-indicator.desktop
     exists, correct content; dpkg-query Conffiles field empty.
   - Real remove (dpkg -r): the file is genuinely gone immediately
     after remove (previously it survived); state dirs and guardiand
     user still correctly preserved.
   - Real purge (dpkg -P): file, state dirs, and guardiand user all
     gone.
   - Real install -> remove -> install cycle: the file is restored
     exactly once after reinstall (identical md5sum both installs, a
     single file at the target path, no duplicate/stale copy).
   - Forbidden-evidence re-scan of the rebuilt .deb (full dpkg-deb -x
     extraction, grepped for "guardiang7caller" and "polkit.addRule",
     plus a filename search for *.rules): clean, nothing found.
   - Privilege regression re-check on the reinstalled, restarted
     services: guardian-daemon Uid=115(guardiand), guardian-helper
     Uid=0(root), both with an all-zero capability set and
     NoNewPrivs=1 -- unchanged from before this repair.
   - Full workspace validation in the VM: cargo fmt --check clean,
     cargo clippy --workspace --all-targets --all-features -- -D
     warnings clean (0 warnings), cargo test --workspace: 292 passed,
     0 failed -- exact match to the pre-repair baseline.

   StateDirectoryMode (the other, separate finding noted above and by
   the earlier independent review) was deliberately left unchanged by
   this repair: it is inherited from already-accepted G7 behavior, the
   runtime directory mode is 0755, sensitive contents remain protected
   by ownership and file-level modes (0600/0700, cross-process access
   independently denied via `sudo -u guardiand` read tests), and it is
   not a G9 packaging regression. It is not coupled to this repair and
   may be revisited separately in a future hardening pass if desired.
