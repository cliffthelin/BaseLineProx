Wave 1 real-VM authorization transcripts (guardian-g9, Ubuntu 26.04 LTS,
polkitd 127-2ubuntu1, systemd 257/258 series shipped with 26.04).

All calls below are real `busctl`/`gdbus` invocations against the real,
running `guardian-helper.service` (built from this handoff's implementation,
release profile, no evidence-hooks feature unless noted) on the real system
bus, mediating the real `org.freedesktop.systemd1.manage-units` policy via
the evidence-only fixture `60-wave1-evidence.rules` (see that file in this
directory) installed only in this disposable VM.

=== W1-VM-002: real, denied local user is rejected ===
$ sudo -u wave1denied gdbus call --system --dest io.github.cliffthelin.GuardianHelper1 \
    --object-path /io/github/cliffthelin/GuardianHelper1 \
    --method io.github.cliffthelin.GuardianHelper1.RestartCapability 'cups-restart' false
Error: GDBus.Error:io.github.cliffthelin.Guardian1.Error.NotAuthorized: authorization denied for org.freedesktop.systemd1.manage-units

`wave1denied` is denied by the fixture unconditionally for manage-units --
this is guardian-helper's own mediated authorize_provider_request check
denying the real caller under the real (fixture) systemd policy, not a
direct-to-systemd test.

=== W1-VM-007 (3): mismatched verb is denied ===
$ sudo -u wave1wrongverb busctl call --system io.github.cliffthelin.GuardianHelper1 \
    /io/github/cliffthelin/GuardianHelper1 io.github.cliffthelin.GuardianHelper1 \
    RestartCapability sb 'cups-restart' false
Call failed: authorization denied for org.freedesktop.systemd1.manage-units

`wave1wrongverb` is granted manage-units by the fixture ONLY for
unit=cups.service AND verb=stop -- since RestartCapability's real
`RestartUnit` call always presents verb=restart, this user is correctly
denied. Native cross-check: `sudo -u wave1wrongverb systemctl restart
cups.service` -> "Failed to restart cups.service: Access denied" (identical
denial via the direct systemd path, confirming the fixture and mediated
check track the same real policy).

=== W1-VM-007 (5): guardian-helper's own root identity is never sufficient ===
Every RestartCapability call above was issued while `guardian-helper` itself
runs as root (systemd `User=root`, matching the deployed
`guardian-helper.service`). `wave1denied`'s denial above, and
`wave1wrongverb`/`wave1wrongunit`'s denials, each prove root/trusted
identity is not what is being evaluated -- the fixture only ever branches on
`subject.user`/`action.lookup(...)`, which the mediated
`CheckAuthorization` request (see checkauth-comparison.txt) shows carries
the real original caller's own bus name as `subject`, never
guardian-helper's.

=== W1-VM-007 (4): no hypothetical Guardian-owned action could substitute ===
No Guardian-owned `.policy` action for systemd restart exists anywhere in
this build (W1-AUTH-005, mechanically checked by
`polkit_action_gains_no_systemd_restart_variant` in
crates/guardian-core/tests/wave1_authorization_contract.rs) -- there is
structurally nothing such a substitution could even name. Confirmed by
inspection of the real, installed `PolkitAction` enum
(`crates/guardian-core/src/authorization.rs`): five variants, four
`guardian.test.*` fixtures plus `io.github.cliffthelin.guardian.g7.bounded-write`,
none referencing systemd.

=== W1-VM-004: concurrent human + Guardian-issued restart ===
See w1_vm_004.txt. A manual `sudo systemctl restart cups.service`
(backgrounded) issued immediately before a Guardian-mediated
RestartCapability call for the same unit: Guardian's own call succeeded
(Committed), and the real cups.service journal shows systemd processing
two Start sequences for the unit without corruption, converging on
ActiveState=active/SubState=running/Result=success. systemd's own
job-merging/queuing is what allows both restart requests to resolve
without Guardian or the manual restart clobbering each other's view of
success.

continuing). Persisted transaction 40008000-0000-0001-18d3-2d73ccd6a68b.txn:
  state=rollback_failed, apply_outcome=confirmed_success,
  last_observation=ambiguous, rollback_result=confirmed_failed
Never RolledBack, never a fabricated success, never an infinite retry loop
-- the transaction reached the real, existing RollbackFailed terminal state
exactly as G4's `classify()`/`RollbackOutcome::terminal_state()` require,
and the caller received `GuardianErrorCategory::RollbackFailed` honestly.
