## 2026-09-19 ~22:xx - Tab key doesn't switch tabs

**Requested via:** chat
**Context:** Textual's `Screen` has a default `Binding("tab",
  "app.focus_next", ...)` that wins over a plain App-level binding of
  the same key, so an App-level `("tab", "next_tab", ...)` entry was
  silently never firing.
**Considered:** Rebinding at the Screen subclass level vs. using
  Textual's `priority=True`, which is checked App-down before the
  normal widget-up resolution that let Screen's default win.
**Requirement determined:** Tab must switch tabs (Hardware/Network/
  Chat/Console), not just cycle focus.
**Files changed:**
  - baseline/bin/baseline — `Binding("tab", "next_tab", priority=True)`.
**Verification:** Confirmed via direct inspection of installed Textual
  2.1.2 source (`_tabs.py`, `screen.py`, `binding.py`) for the
  priority-resolution order, then live: Tab cycled all four tabs.
**Pointer update:** ui row added to INDEX.md.
**Docs update:** none.

## 2026-09-19 ~22:xx - Down arrow doesn't enter a table from the tab bar

**Requested via:** chat ("Arrow down should move out of the header
  tabs.")
**Context:** `DataTable` binds "down" itself for row-cursor movement, so
  a non-priority App-level "down" binding only fires when focus is
  *not* already on a table. The original guard checked
  `isinstance(self.focused, Tab)`, but the tab bar's focused widget is
  actually a `Tabs` (`ContentTabs`) instance, never an individual `Tab`
  - so the condition was always false and Down did nothing.
**Considered:** N/A - straightforward isinstance-target bug once found
  via a headless Textual test harness.
**Requirement determined:** Down, pressed while the tab bar has focus,
  moves focus into the active pane's table/input.
**Files changed:**
  - baseline/bin/baseline — `action_focus_tab_content()`: `isinstance
    (self.focused, Tabs)` (was `Tab`).
**Verification:** Headless pilot test: `focused after down:
  DataTable(id='net_table')`.
**Pointer update:** ui row updated in INDEX.md.
**Docs update:** none.

## 2026-09-20 01:0x - BaselineOS crashing to a traceback, then respawning

**Requested via:** chat ("I keep getting an error page that shows code
  but then falls back to the main page")
**Context:** Textual's own `_handle_exception()` is explicit: any
  unhandled exception "always results in the app exiting." Under
  `Restart=always` that reads as "crash screen, then back to the main
  page." Root cause for this specific report was the MarkupError issue
  (hardware/001.md, network/001.md), but the *pattern* - one bad
  render taking down the whole app - was worth closing generally, not
  just for that one trigger.
**Considered:** Fixing only the specific MarkupError triggers found vs.
  also adding a structural safety net, since Textual's crash-on-any-
  exception behavior means the next unknown bug would do the same
  thing.
**Requirement determined:** A single bad row/render/handler must be
  contained (logged, skipped) rather than crashing the whole process,
  on top of - not instead of - fixing the specific triggers found.
**Files changed:**
  - baseline/bin/baseline — `_safe()` decorator (catches, logs to
    `/var/log/baseline/ui_errors.log`, doesn't re-raise) applied to
    render callbacks and event handlers; `exit_on_error=False` added to
    every `@work(...)` decorator.
**Verification:** Confirmed via Textual source
  (`worker.py`: `if self.exit_on_error: app._handle_exception(...)`).
  Re-ran the full crash-reproduction sweep (all 77 real hardware rows +
  modals) after landing this, zero exceptions escaping to the app
  level.
**Pointer update:** ui row updated in INDEX.md.
**Docs update:** none.

## 2026-09-20 01:3x - modal button coloring, toggle-not-buttons, arrow control

**Requested via:** chat ("Modals button concept or coloring is bad...
  there should be arrow control... The things you have listed should be
  toggles not buttons and the header and footer of the app must be
  persistent.")
**Context:** `Button`/`RadioSet`/`ToggleButton` were using Textual's
  default `$theme-variable` styling ($primary, $surface, etc.) -
  exactly the class of thing already known to render illegibly under
  `TERM=linux`. Set-as-Primary/Set-as-Fallback were two momentary
  buttons, not a real toggle, and had no arrow-key navigation between
  them. Every modal, being a separate `Screen`, hid the main app's
  Header/Footer while open.
**Considered:** Custom key-by-key focus wiring for Primary/Fallback vs.
  Textual's own `RadioSet`, which already binds Up/Down/Left/Right
  between options and Enter/Space to select - chose RadioSet since it's
  a real, built-in toggle rather than a hand-rolled one.
**Requirement determined:** Every color explicit hex (no theme
  variables); Primary/Fallback a real arrow-navigable toggle; every
  modal shows its own Header/Footer so they never visually disappear.
**Files changed:**
  - baseline/bin/baseline — `MODAL_CSS` (shared explicit-hex styling
    for Button/RadioSet/ToggleButton, reused by all three modals);
    `RadioSet`/`RadioButton` replacing the two buttons in
    `ConnectionModal` (see network/001.md for the fuller rewrite);
    `yield Header(show_clock=True)` / `yield Footer()` added to every
    modal's `compose()`.
**Verification:** Headless tests: confirmed Header/Footer present in
  every modal screen (`bool(screen.query(Header))` /
  `bool(screen.query(Footer))`), confirmed RadioSet Up/Down changes
  selection, confirmed Left/Right moves between Save/Close buttons
  without disturbing RadioSet's own arrow handling (widget-level
  bindings win over the screen-level fallback when focused).
**Pointer update:** ui row updated in INDEX.md.

## 2026-09-20 12:3x - Down/Shift+Tab stopped working after switching tabs

**Requested via:** chat ("Down is not working" / "I lost both shift tab
  and arrow down. So I can't verify yet.")
**Context:** Reproduced the exact sequence: focus a table with Down,
  open then close a modal, switch tabs with Tab - `self.focused` became
  `None`. `action_next_tab()` never explicitly managed focus; switching
  panes leaves focus on whatever was focused in the now-hidden old
  pane, and Textual doesn't reassign it to anything. Both Down and
  Shift+Tab require focus to be on the tab bar specifically
  (`action_focus_tab_content` checks `isinstance(self.focused, Tabs)`),
  so a stale/None focus silently broke both - a pre-existing bug not
  caused by the same day's other changes, just newly exposed by testing
  a more realistic navigation sequence.
**Considered:** Making the focus checks more lenient (`self.focused is
  None or isinstance(...)`) vs. fixing the actual cause - focus not
  being managed on tab switch - so the invariant ("tab bar has focus
  right after switching") holds the way it does at initial app start.
**Requirement determined:** After switching tabs by any path (fresh
  start or after a modal round-trip), Down and Shift+Tab must both
  work immediately.
**Files changed:**
  - baseline/bin/baseline — `action_next_tab()` explicitly calls
    `tabbed.query_one(Tabs).focus()` after switching the active pane.
**Verification:** Headless test reproducing the exact reported
  sequence (focus table -> open ConnectionModal -> close it -> switch
  tabs twice -> Down): failed before the fix (`focused: NoneType`),
  passed after (`focused: ContentTabs`, then correctly moved to the
  pane's content on Down).
**Pointer update:** ui row updated in INDEX.md.
**Docs update:** none.
