## 2026-09-19 ~23:30 - Hardware tab showing nothing (real root cause)

**Requested via:** chat ("You are not displaying any hardware.")
**Context:** After earlier fixes (HOME env, tty-stdin for inxi - see
  boot/001.md) the Hardware tab was *still* empty. Traced with a
  headless Textual pilot test against the real deployed app: the
  worker's body never even started executing.
**Considered:** More inxi-environment theories (red herrings from
  earlier) vs. inspecting Textual's own worker-scheduling behavior
  directly.
**Requirement determined:** `collect_hardware()`'s thread body must
  actually run every time `on_mount()`/manual refresh calls it.
**Files changed:**
  - baseline/bin/baseline — gave `collect_hardware()` and
    `collect_network()` distinct `group=` values on their `@work(...)`
    decorators. Root cause: both were `exclusive=True` with no
    explicit group, so both defaulted to Textual's shared `"default"`
    group - and `exclusive=True` cancels every other worker in the
    same group. `on_mount()` calls `collect_hardware()` immediately
    followed by `collect_network()`, so the second call was silently
    cancelling the first before its thread body ever ran.
**Verification:** Headless pilot test against the live host: deleted
  `/var/lib/baseline/hardware_snapshot.json`, restarted the service,
  confirmed the file reappeared with real data within 5s (previously
  never appeared at all, even after 13+ seconds).
**Pointer update:** hardware row added to INDEX.md.
**Docs update:** none.

## 2026-09-20 00:3x - MarkupError crash opening the Drives row

**Requested via:** chat ("I keep getting an error page that shows code
  but then falls back to the main page... From the details page and
  moving through them.")
**Context:** inxi's own SMART output contains literal text like
  `written-units: 781,581,482 [400 TB]`. Textual's `Static`/`Label`
  parse their content as markup by default; `[400 TB]` isn't valid
  markup syntax, so opening the Drives row's Details tab raised
  `MarkupError` - and Textual treats *any* unhandled exception as fatal
  to the whole app (confirmed in Textual's own `_handle_exception`:
  "Always results in the app exiting"). `Restart=always` respawned the
  process, which read as "crash screen, then back to the main page."
**Considered:** Sanitizing/stripping bracket characters from collected
  data vs. telling the widgets not to parse markup at all, since the
  data was never meant to be styled - it's raw evidence.
**Requirement determined:** No real collected data (hardware or
  network) may ever be interpreted as markup; opening any row,
  including Drives, must not crash the app.
**Files changed:**
  - baseline/bin/baseline — `markup=False` on every Static/Label
    showing real collected data, in `InfoModal`, `ConnectionModal`, and
    `HardwareModal`. `escape_markup()` used instead for the few
    widgets that keep markup on for genuine styling.
**Verification:** Reproduced the crash first against the live host's
  real Drives data (confirmed the exact `MarkupError`), then confirmed
  it no longer reproduces: scrolled through all 77 real rows and
  opened/closed every one of their modals with zero exceptions.
**Pointer update:** hardware row updated in INDEX.md.
**Docs update:** none.

## 2026-09-20 00:2x - no keyboard way out of the Hardware modal

**Requested via:** chat ("Now there is no way out of detail pages.")
**Context:** `HardwareModal`'s own `TabbedContent`
  (Details/Description/.../Configuration) absorbs every Tab press to
  cycle its five panes, so Tab alone could never reach the Close
  button - and nothing bound Escape yet.
**Considered:** Making Tab exit the pane-cycle after reaching the last
  pane (fragile, surprising) vs. a dedicated, always-available Escape
  binding.
**Requirement determined:** Escape must close the modal from any state
  inside it, regardless of which tab or widget has focus.
**Files changed:**
  - baseline/bin/baseline — `Binding("escape", "close_modal", ...)` +
    `action_close_modal()` on `HardwareModal` (and, for consistency,
    `InfoModal`/`ConnectionModal`).
**Verification:** Headless test: opened the modal, pressed Tab twice
  (cycling panes), pressed Escape, confirmed `screens: 1` (closed).
**Pointer update:** hardware row updated in INDEX.md.
**Docs update:** none.

## 2026-09-20 00:5x - Save and Close / Close without saving

**Requested via:** chat ("(s) Save and Close, (esc) Close without
  saving.")
**Context:** Escape-only exit gave no way to distinguish "commit
  changes" from "discard changes" once the modal might ever hold
  editable state.
**Considered:** Making Escape itself smart about pending changes vs. a
  second, explicit key with its own clearly-labeled action - chose the
  latter since it's unambiguous and matches the pattern the user asked
  for by name.
**Requirement determined:** `s` commits (currently a no-op placeholder,
  since Configuration has no real fields yet - documented as such so
  it doesn't read as fake functionality); `esc` always discards and
  closes.
**Files changed:**
  - baseline/bin/baseline — `Binding("s", "save_and_close", ...)`,
    `action_save_and_close()`, visible "Save and Close"/"Close without
    saving" buttons, a real `Footer()` showing both hints.
**Verification:** Headless test confirming both bindings dismiss the
  modal; buttons visually confirmed on the live device by the user.
**Pointer update:** hardware row updated in INDEX.md.
**Docs update:** none.
