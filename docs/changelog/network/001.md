## 2026-09-19 ~23:50 - Wi-Fi/Cellular/Tether wrongly shown Unreachable

**Requested via:** chat ("How is the WiFi value unreachable. Did you
  break it? If not it's Available.")
**Context:** "No carrier -> Unreachable, not physically connected" was
  applied to every interface type. That phrase is only true for wired
  Ethernet - Wi-Fi/Cellular Modem/Phone Tether can lack carrier simply
  because nothing has associated yet, which is recoverable.
**Considered:** A per-interface-type exception list inline vs. a real
  `is_wired()` helper keyed off the driver name, reusing the existing
  `FRIENDLY_DRIVERS` classification.
**Requirement determined:** Wired-with-no-carrier stays Unreachable
  (nothing fixes that without a cable); every other type with no
  carrier shows Available.
**Files changed:**
  - baseline/lib/network.py — `WIRED_DRIVERS`, `is_wired()`,
    `list_interfaces()` now includes `"wired"`.
  - baseline/bin/baseline — `_render_network()` branches on it.
**Verification:** Headless pilot test against live interfaces: Wi-Fi
  and Cellular Modem (no carrier) now show `Available`; the USB dock
  Ethernet (no carrier, wired) still shows `Unreachable`.
**Pointer update:** network row added to INDEX.md.
**Docs update:** none.

## 2026-09-19 ~23:55 - Network tab blank after error-containment change

**Requested via:** chat (indirect - surfaced while hardening render
  callbacks against crashes)
**Context:** `_render_network()` calls `table.clear()` then adds rows
  in a loop; if any single row's data raised an exception partway
  through, the table was left fully cleared with nothing re-added.
**Considered:** Wrapping the whole render in one try/except (loses
  every other row too) vs. wrapping each row's `add_row()` call
  individually.
**Requirement determined:** One bad row must not blank the whole table
  - every other row must still render.
**Files changed:**
  - baseline/bin/baseline — per-row try/except around
    `table.add_row(...)` in both `_render_network()` and
    `_render_hardware()`, logging failures to
    `/var/log/baseline/ui_errors.log` instead of losing them silently.
**Verification:** Headless test with a deliberately malformed row
  confirmed the other rows still render; real-world trigger (see the
  markup-crash entries in this file and hardware/001.md) stopped
  blanking the table after this landed.
**Pointer update:** network row updated in INDEX.md.
**Docs update:** none.

## 2026-09-20 00:2x - Unicode traffic arrows removed (TERM=linux risk)

**Requested via:** chat (investigating a reported crash; not fully
  confirmed as the cause, but removed as a real, verified risk)
**Context:** `interface_traffic_label()` used "down"/"up" as Unicode
  arrow glyphs (down arrow / up arrow). Confirmed the codebase's only
  non-ASCII characters were these two, on a project that has already
  hit multiple `TERM=linux` rendering issues this session.
**Considered:** Keeping the arrows (cosmetically nicer) vs. plain ASCII
  words, given the bare framebuffer console's font may not have those
  glyphs at all.
**Requirement determined:** No non-ASCII characters anywhere in
  rendered output, full stop.
**Files changed:**
  - baseline/lib/network.py — `interface_traffic_label()`: `"down
    {...} up {...}"` instead of arrow glyphs.
**Verification:** `grep -rnP '[^\x00-\x7F]'` across the whole
  `baseline/` tree returns zero matches.
**Pointer update:** network row updated in INDEX.md.
**Docs update:** none.

## 2026-09-20 ~12:xx - ConnectionModal: bridged identity, alias, enable/disable, lifeline position

**Requested via:** chat ("the modal should add details that bridge
  anything from the other tabs into on place... manufacturers details
  if it's on the motherboard or on a port... driver... rename the
  Alias... disable it... show its position in the workflow.")
**Context:** The Network tab's per-interface modal only showed a
  Primary/Fallback toggle - no hardware identity, no way to rename or
  disable the interface, no visibility into where this device sits in
  the Lifeline chain (NIC->driver->carrier->address->gateway->DNS->
  internet->LLM).
**Considered:** Re-parsing inxi's Network section for vendor/model data
  (already known to be unreliably paired to a specific ifname - see
  hardware/001.md's full-inventory entry) vs. `udevadm info -q
  property`, which is keyed directly by device path and works
  uniformly for both PCI (onboard) and USB (dock/tether) devices via
  udev's own hardware database. Chose udevadm.
**Requirement determined:** Opening a Network row must show real
  manufacturer/model/connection-type/driver for that exact device, a
  renameable alias persisted across restarts, a genuinely-working
  enable/disable control, and, when this device is the one actually
  carrying the lifeline right now, its real pass/fail position in that
  chain.
**Files changed:**
  - baseline/lib/network.py — `load_aliases()`/`save_alias()`
    (`/etc/baseline/interface_aliases.json`, used by `friendly_name()`
    everywhere including the Hardware tab); `device_details()` (udevadm
    query); `is_admin_up()`/`set_admin_state()` (real `ip link set`).
  - baseline/bin/baseline — `ConnectionModal` rewritten: identity block,
    alias `Input`, enable/disable `Switch`, Primary/Fallback as a real
    `RadioSet` toggle (replacing two immediate-action buttons),
    lifeline-position text built from the same `facts` list
    `check_lifeline()` already produces, Save-and-Close/Close-without-
    saving.
**Verification:** Live against the real Ethernet device: `{'driver':
  'e1000e', 'connection': 'Onboard (PCI)', 'chipset_vendor': 'Intel
  Corporation', 'model': 'Ethernet Connection (4) I219-LM',
  'manufacturer': 'Dell Inc.'}`; alias save/reload round-tripped
  through `network.load_aliases()`; lifeline checklist showed all 8
  real stages as OK for the active device. Deliberately did *not*
  live-test the disable action against the interface carrying the
  active SSH session, to avoid dropping it - noted as a real,
  intentionally-disruptive action, not cosmetic.
**Pointer update:** network row updated in INDEX.md.
**Docs update:** none yet - candidate for a short note on
  `interface_aliases.json` in BAREMETAL_BRINGUP_NOTES.md or a new
  doc, since it's a new persistent state file outside `/etc/baseline`'s
  previously-documented `network_preference.json`/`harness.env`.
