## 2026-09-19 23:xx - inxi refuses to run without a real tty on stdin

**Requested via:** chat
**Context:** `hardware.collect()` intermittently failed with `Error 1:
  You can't run option help in an IRC client!` - inxi's own IRC-safety
  heuristic shells out to `tty` against its stdin; a non-tty stdin trips
  it into refusing most options.
**Considered:** Suppressing the check via an inxi flag (none exists for
  this) vs. explicitly handing inxi a real, openable tty fd for stdin
  regardless of what the calling process's own stdin looks like.
**Requirement determined:** `hardware.collect()` must succeed
  regardless of whether its own stdin happens to be a tty.
**Files changed:**
  - baseline/lib/hardware.py — `_explicit_tty_stdin()` opens the
    process's own controlling tty by name and passes that fd as
    `stdin=` to the inxi subprocess call.
**Verification:** Reproduced the failure via SSH (no pty) repeatedly,
  confirmed the fix using an explicitly-opened tty fd resolved it in a
  loop of 15 consecutive calls (`ok: 15 fail: 0`).
**Pointer update:** boot row updated in INDEX.md.
**Docs update:** none.

## 2026-09-20 00:1x - getty.target ordering cycle blocking boot

**Requested via:** chat (user hit a frozen boot screen live: "[ SKIP ]
  Ordering cycle found, skipping getty.target")
**Context:** The original unit had `After=multi-user.target` +
  `Before=getty.target` together, which forms a real systemd dependency
  cycle (multi-user.target's own graph pulls in getty.target). systemd's
  cycle-breaker drops getty.target from the transaction entirely,
  meaning *no* tty on the machine gets a login prompt, not just tty1.
**Considered:** Removing just one of the two directives vs. switching to
  the standard "replace one specific getty" idiom
  (`Conflicts=getty@tty1.service` + `After=getty@tty1.service`, no
  `Before=` on the aggregate target at all).
**Requirement determined:** Boot must reach a working console (Baseline
  or a getty) without a dependency-cycle warning, on every boot, not
  "usually."
**Files changed:**
  - boot/baseline.service — removed `After=multi-user.target` and
    `Before=getty.target`; added `After=getty@tty1.service` (kept the
    existing `Conflicts=getty@tty1.service`).
**Verification:** User confirmed boot reached Baseline on the next
  attempt after the fix was deployed; the ordering-cycle message did not
  reappear on subsequent reboots.
**Pointer update:** boot row updated in INDEX.md.
**Docs update:** none.

## 2026-09-20 12:xx - console font/glyph-map corruption ("garble")

**Requested via:** chat, with a live photo of the corrupted screen
**Context:** After a batch of restarts during testing, tty1 started
  rendering real text as wrong/missing characters (e.g. "Hardware" as
  "zardware"). Confirmed this survives a plain `systemctl restart` -
  restarting the *process* doesn't touch the kernel's loaded console
  font/Unicode glyph-mapping table, only `TTYReset`/`TTYVHangup`
  (termios flags) do, and neither of those resets the font table.
**Considered:** Rebooting the whole machine (would likely clear it, but
  doesn't explain or prevent recurrence) vs. finding the actual kernel
  API that owns font state and resetting *that* directly.
**Requirement determined:** The font/glyph table must self-heal on
  every service start, without depending on a full reboot, and the fix
  must be re-verifiable on demand (see the same-day entry in this file
  for the standalone check).
**Files changed:**
  - boot/baseline.service — added
    `ExecStartPre=-/usr/bin/setfont /usr/share/consolefonts/Lat15-Fixed16.psf.gz -C /dev/tty1`
    (leading `-` so a missing font file on a different image doesn't
    block startup).
**Verification:** Ran `setfont` manually first (confirmed it fixed the
  live corrupted screen per user report), then confirmed
  `ExecStartPre` runs and exits `status=0/SUCCESS` via
  `systemctl status baseline.service` on a fresh restart.
**Pointer update:** boot row updated in INDEX.md.
**Docs update:** none yet - candidate for BAREMETAL_BRINGUP_NOTES.md.

## 2026-09-20 ~14:00 - standalone, re-runnable font check + provisioning hook

**Requested via:** chat ("make a unit test for that which is check and
  fixed if needed at each deploy")
**Context:** The `ExecStartPre` fix above only runs on a service
  restart/boot - there was no way to verify (or re-apply) the fix as an
  explicit, visible step right after a deploy, without waiting for the
  next restart.
**Considered:** A Python check (consistent with the rest of the
  codebase) vs. a shell script (matches `provision.sh`'s existing
  style, and the fix itself is a shell command with no meaningful
  Python API). Chose shell. Also considered trying to *detect*
  corruption before fixing it - no non-invasive kernel API exposes
  "is my glyph table sane," so the check and the fix are the same
  idempotent action (loading a known-good font is safe to do even when
  nothing is wrong).
**Requirement determined:** A standalone script must exist that (a)
  confirms the expected font file is present, (b) loads it onto tty1,
  (c) reports PASS/FAIL with real error output, (d) is safe to re-run
  at any time, and (e) is wired into provisioning for fresh installs.
**Files changed:**
  - tests/console_font_check.sh — new; check-and-fix script.
  - boot/provision.sh — calls it right after installing the systemd
    unit.
**Verification:** Deployed to `/opt/baseline/tests/console_font_check.sh`
  on the live host and ran it: `PASS: .../Lat15-Fixed16.psf.gz loaded
  cleanly on /dev/tty1`.

## 2026-09-20 14:3x - Display fact reimplemented without the /dev/tty1 open

**Requested via:** chat ("let's reimplement any reverted work due to the
  garbled text from earlier")
**Context:** See hardware/001.md's revert entry - the original
  `display_mode()` opened `/dev/tty1` as a new fd from within the
  already-running app to query the character grid via `TIOCGWINSZ`,
  and garble followed. Not proven as the exact mechanism, but the user
  wanted the feature back done more carefully.
**Considered:** Dropping the character-grid field entirely vs. getting
  it a different way that avoids opening any new tty fd.
  `os.get_terminal_size()` reads the process's own already-open stdout
  (fd 1) - the exact same tty, zero new file descriptors - so the field
  was kept.
**Requirement determined:** Same display-mode data as before, with no
  new file descriptor ever opened to a tty device node from within the
  running app.
**Files changed:**
  - baseline/lib/hardware.py — `display_mode()` restored, character
    grid now via `os.get_terminal_size()` instead of opening
    `/dev/tty1` directly.
**Verification:** Tested standalone via SSH first (no live app
  involved) to confirm no crash; then a full headless crash-sweep
  against the live app (74 rows, all modals opened/closed cleanly);
  then deployed and restarted the actual service; user confirmed the
  screen looked clean before I proceeded to the next task.
**Pointer update:** boot row updated in INDEX.md; hardware row updated.
**Docs update:** none.

## 2026-09-20 14:3x - Proxmox<->BaselineOS round trip

**Requested via:** chat ("a return to ProxMox and then ProxMox return
  to BaselineOS")
**Context:** Baseline owns tty1 exclusively (`Conflicts=
  getty@tty1.service`), replacing its login prompt entirely - there was
  no way to reach a normal Proxmox host shell from the physical console
  without SSH.
**Considered:** Actually stopping baseline.service and starting
  getty@tty1 in its place (more disruptive, loses Baseline's own state)
  vs. using a *different* VT for the Proxmox login and leaving Baseline
  running undisturbed on tty1 underneath. Confirmed live that switching
  to an unused VT via `chvt 2` alone is enough - systemd-logind
  auto-starts `getty@tty2.service` on first switch, no unit needs
  enabling by hand.
**Requirement determined:** One keypress in Baseline reaches a real
  Proxmox login console; one word typed there returns to Baseline,
  without stopping or losing Baseline's own running state either way.
**Files changed:**
  - baseline/bin/baseline — `Binding("p", "return_to_proxmox",
    "Proxmox")`, `action_return_to_proxmox()` runs `chvt 2`.
  - boot/baseline-return.sh — new; defines a `baseline` shell function
    (`chvt 1`) and prints a one-line hint, only on an actual console
    tty (`/dev/tty[2-6]`, never over SSH, so a remote session can't
    surprise-switch the physical screen).
  - boot/provision.sh — installs `baseline-return.sh` to
    `/etc/profile.d/`; also backfilled three `cp` lines it was already
    missing for netpref.py/providers.py/tether.py (unrelated to this
    feature, noticed while editing the same file).
**Verification:** Live: `chvt 2` switched the active VT and
  `getty@tty2.service` came up `active running`; `chvt 1` switched
  back immediately (verified via `/sys/class/tty/tty0/active`).
  Sourced `baseline-return.sh` directly and confirmed `type baseline`
  shows the function correctly. Full crash-sweep (hardware + modals)
  run before restarting the live service.
**Pointer update:** boot row updated in INDEX.md.
**Docs update:** none yet - candidate for BAREMETAL_BRINGUP_NOTES.md
  (the systemd-logind autovt behavior is exactly the kind of
  non-obvious gotcha that doc already collects).
