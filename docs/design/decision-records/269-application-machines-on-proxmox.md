# 269 - Application machines on Proxmox: Claude, ChatGPT, LM Studio, Ollama, VS Code, Spotify

Date: 2026-10-17. Status: the catalogue entries, the install scripts, the first-boot seed and the Proxmox command lines are built and tested; the Ollama install was run for real (below); NOTHING here has been run on a real Proxmox host.

## Operator direction (2026-10-17)
Kasm already has these as stand-alone workspaces, so Kasm is satisfied. From Proxmox they must be added **with a base matching the Linux type**, preferably able to run on their own, **with network access to the system drives and to other network servers**: Claude Code desktop, ChatGPT, LM Studio, Ollama, VS Code, Spotify. Asked how, the operator chose: a VM per app with Ollama in an LXC container, and "any of the above" for drives and network (virtiofs, NFS/SMB, open service ports), left to my judgement.

## Correction: no separate login, the Proxmox user is the user
Earlier versions of the ready-made VMs (DR267) and this work gave each VM its own account (`baseline-admin`, then a test user) with a generated one-time password. The operator's correction: **the user is already logged in from Proxmox and persists until more Proxmox users are made.** So now the VM has one account, the Proxmox user's name (kept once in `owner.json`; `root` or an odd name becomes `owner`), uid 1100 on every system, **no password**, sudo without a prompt, signed in at the console (GDM on Debian and Ubuntu, SDDM on CachyOS). Nothing is generated, stored or shown. Checked on the real Debian and Ubuntu bases: the account exists at uid 1100, its password is locked, `sudo -n` works, the hostname is set. The web handler passes the signed-in user's name, never anything from the request body.

## How it is built
- **Catalogue (`app_catalogue.py`, `config/app-catalogue.json`)** gains the six, with routes for each Linux type: Flatpak (VS Code, Spotify, which exist on Flathub; Claude, ChatGPT, LM Studio and Ollama do not), the publisher's Debian package (Claude, Spotify and ChatGPT on Debian and Ubuntu: the file and its SHA-256 are found from the publisher's own Debian package index; ChatGPT has no index, so its first download's hash is recorded), the LM Studio AppImage (the versioned address its download link redirects to; no hash is published, so the first fetch's is recorded), the Ollama release tarball (its SHA-256 from the release data on GitHub), pacman (Ollama on Arch-family systems), nix attributes. Where a Linux type has no route (Claude and ChatGPT on Arch-family, Fedora-based and NixOS systems: they publish only Debian packages), the answer says so and nothing is guessed.
- **`app_environment.py`**: `plan` picks the base and the route for that Linux type and the command that starts the app; `seed_extra` adds to the base's seed: the install script, a marker when it finished, the autostart entry, and the mounts; `create_vm` makes the VM from the base (`prebuilt_environment.create` with those additions). Mount rows for NFS and SMB (`_netdev,nofail`, so a missing server never stops the boot; SMB names a credentials FILE on the machine and a password is refused) and virtiofs; the Proxmox command lines for a virtiofs directory mapping and the VM device; and the Ollama container.
- **Ollama in an LXC**: created from the Debian template, unprivileged, firewall on, its models on a mount point from a constant volume under `/mnt`, started at boot, and a firewall file allowing only the stated address range to reach port 11434 (policy in: drop). The install script is pushed and run with `pct exec` after it starts.

## What was run
The Ollama script (the same one the container runs), on a throwaway layer over the Debian base with a second blank disk mounted at `/models` standing in for the constant volume: it downloaded the pinned release (SHA-256 from the release data, checked), installed it under `/opt/ollama` with its own unprivileged user, started the service, and Ollama answered on every address (`*:11434`: "Ollama is running", version 0.40.6) with the models folder on the separate disk, owned by the service user. That proves the script, the service unit, the listening address and the constant-volume use; it was a VM not an LXC.

## Not verified
- Any of it on a real Proxmox host: the virtiofs directory mapping and device (Proxmox 8.4 and later), the container creation and the firewall file, the VM seed's first-boot install and autostart for the desktop apps.
- The desktop applications actually installing and starting at login in their VMs (only the install routes for the catalogue's browsers and Ollama were exercised; the scripts for the deb, AppImage and Flatpak routes are syntax-checked and unit-tested).
- NFS and SMB mounts (no file server was available here).
- The Debian base still has the installer's own `baseline-admin` account (locked) and Ubuntu its `ubuntu` account; neither can be signed in to, and the owner is uid 1100 so they never collide.
