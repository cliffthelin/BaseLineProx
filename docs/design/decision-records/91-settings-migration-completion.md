# Decision record: completing the settings-to-SQL migration

Status: **implemented, unit-tested (1420/1420 full suite, up from 1414). Items 1-5 below are done; item 6 (production verification) is explicitly not, and needs a real system-level action outside this repo before it can be.**

## What was asked

"What further steps are needed to complete the settings to SQL migration?" then, given a prioritized list of six real gaps: "They all need fixed, just queue them up and resolve them."

## The six items, and what was done

1. **`registry.py` schema versioning.** Added `SCHEMA_VERSION`, `PRAGMA user_version` tracking, and a `register_migration(from_version, upgrade_fn)` mechanism that walks a database forward one version at a time. No real migration exists yet (only version 1 has ever shipped) - this is the scaffolding a future table change needs before it can ship safely, not a change being made now. A version-0 database (sqlite's own default, indistinguishable from "created before this scheme existed") is treated as version 1 and carried forward normally. Refuses outright to open a database whose stamped version is *newer* than the running code understands, rather than risk corrupting it.

2. **`export_bootstrap_snapshot` wired into real use.** It existed, tested, and uncalled since decision record 87. `drive_admin.build_self_installer` now calls it once for all three `self_installer.*` values instead of three separate `get_setting` calls repeating the same (group, key) pairs - a real simplification, not just closing a "dead code" finding.

3. **`netpref.py`'s `network_preference.json` migrated onto `settings_store.py`.** A new `"network"` group (`preferred_primary_interface`, `preferred_fallback_interface`) registered via `register_schema` - the first real external use of that extensibility mechanism outside `settings_store.py`'s own seed data. `load_preference`/`save_preference` keep their exact prior signatures and return shape; `bin/baseline` (the only real caller) needed no changes. This module had no test coverage at all before this pass - five new tests added.

4. **`network.py`'s `interface_aliases.json` migrated onto `registry.py` directly, not through `settings_store.py`.** A real design distinction, not an oversight: one interface name per physically-present NIC is a dynamic key space known only at runtime (hardware-dependent), not a fixed set of (group, key) pairs `settings_store.SettingDef` expects declared up front - exactly the case `registry.py`'s generic entries exist for. Also had zero test coverage before this pass - seven new tests added, including a real regression case (clearing a never-set alias is a no-op, not an error).

5. **`config_pipeline.py`/`control_panel_web.py`/`backup_restore.py`'s shared `install-config.json` reviewed and deliberately left alone.** This is an external artifact exported by a separate tool (the Install Configurator), placed on the target disk by an operator before first boot, and read/diffed/backed-up as a *file* by design (`backup_restore.py` includes it in its own file-based backup manifest alongside `/etc/smartd.conf`). Migrating this to the internal registry would break the actual real-world workflow it exists to support - a human exporting JSON from a separate application isn't going to write into a SQLite file with scope/attribute semantics. Reviewed and excluded on purpose, stated here so it isn't mistaken for a miss.

6. **`settings_web.py`'s `JsonFileStore` renamed to `LocalAppStore` and rewritten onto SQLite**, the single largest piece of this pass. Every public method (`get_user_hash`, `get_elevation_hash`, `add_user`, `settings`, `update_section`, `save_pending_account`, `record_rebuild`) kept its exact prior signature and return shape, so no caller needed logic changes - only `JsonFileStore` -> `LocalAppStore` renames across the two real consumers (`settings_web.py`'s own standalone server, `scripts_inbox_web.py`'s separate login store) and the test suite. **Deliberately not routed through `registry.py`'s fixed GLOBAL/PROTECTED scope** - `LocalAppStore` is reused by multiple small, independently-deployed local web apps, each at its own injected path (`/tmp/...` for standalone evaluation, `/var/lib/baseline/...` for a real deployment, `/tmp/baseline-scripts-inbox/...` for the separate scripts-inbox app); forcing it onto the machine-wide foundational registry's fixed paths would have broken exactly the "no root, no install required" standalone-evaluation property this class exists to preserve - the same real design tension already resolved once for `sensors_history.db` (decision record 88) and `install-config.json` (item 5 above): some data genuinely belongs to a specific service's own local store, not the machine-wide registry, and forcing unification onto data with a different real shape and lifecycle is a mistake, not thoroughness. Added a real `rebuild_log()` accessor (there was no way to read that back at all under the old JSON shape without reaching into the file directly) and real tests for it.

**Also surfaced while building item 6**: the Admin tab had no visibility into registered dependencies or their check results at all - `dependencies.dump_configuration_snapshot()` existed for troubleshooting but nothing in the actual UI ever called it. `handle_admin_view` now includes every dependency's definition and most recent result in its response; `render_admin_page` renders a real "Dependencies" table (id, level, severity, last result, detail) - read-only by design, matching `handle_admin_view` never triggering a fresh run itself (that stays the adhoc action's job). This closes the "know what is in place" goal decision record 88 originally stated but never gave a UI to.

## Item not done: production-equivalent verification

Nobody has confirmed the PROTECTED-scope checks (`install.self_installer_lvm_preset_valid`/`fqdn_valid`, and now `network.preferred_*_interface`) actually *pass* end-to-end with a real, root-owned `/etc/baseline` present - only that they fail gracefully instead of crashing when it's absent (decision record 90). Closing this for real means creating `/etc/baseline` (root-owned, per the real deployment model) on this development machine - a genuine system-level action outside this repository, not something to do without asking first regardless of a broad "resolve everything" instruction. Unit-test coverage already exercises the identical code path against a writable temp directory and passes cleanly (`test_run_health_check_reports_ok_when_every_dependency_passes`), which is strong but not equivalent evidence to a real root-owned path on real hardware.

## Verification performed

- RED confirmed for the schema-versioning scaffolding (a database stamped one version ahead correctly refuses to open; a gap with no registered migration correctly refuses rather than guessing).
- `netpref.py` and `network.py`'s alias storage had no prior test coverage at all - both now have real, focused suites (5 and 7 tests respectively) exercising the actual migrated behavior, not just import-safety.
- `LocalAppStore`: existing `settings_web.py` test suite (74 tests) passed after the rename/rewrite with only the internal-implementation-detail tests updated (`._read()` access replaced with the new public `rebuild_log()`; a test simulating a pre-sqlite file shape rewritten to remove a real row instead); four new tests added for behavior the old class never had test coverage for (rebuild-log ordering, seeded-account isolation, section-update isolation).
- A real, unmocked smoke test of `LocalAppStore` (not a fake, not pytest) confirmed persistence across separate instances against a real file.
- New Admin-tab dependency-visibility tests (7) covering: definitions listed, a real prior check result reflected, the "never checked" case on a fresh machine, and the rendered page showing/omitting the section correctly.
- Full suite: 1420/1420 (1414 before this record).
