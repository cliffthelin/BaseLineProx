# 271 - No hardware identifiers in the repository; one-to-many is detected, not guessed

Date: 2026-10-18. Status: built and tested (full unit suite); not yet exercised in an installed Proxmox guest with two Proxmox drives attached.

## Operator direction (2026-10-18)
1. The PC401 port still named PC401's serial in code. The operator's point: a table of "the other lane's serials" is a special case; the real problem is any place that assumes exactly one of something (one Proxmox install, one volume group called `pve`, one drive for a serial, one device for a label) and could meet more than one. Detect that, do not pick the first.
2. There must be NO hard-coded serials "or the like" anywhere in the code base. If stored at all they live on git-ignored volumes that are never pushed to GitHub, and count as sub-system data or user data.

## What changed
- **Serials are data, never code.** The lane's own drives are in `/etc/baseline/own-drives` (one serial per line; `SERIAL disposable` for a drive the operator marks reinstallable over old data, which is the development lock). It lives on the persistent admin volume and is written on the installed system itself: the first boot's new `own-drive` step records the drive the system runs from (nothing typed, nothing baked in). `BASELINE_OWN_DRIVES_FILE` names another file for a build or test host. The host-side installer reads its target names from `drives.json` on the build volume (`BASELINE_DRIVES_FILE`), outside the repository.
- **Another lane's drive is recognised by the drive, not by a table.** The identifier stamped on a drive (DR255) carries the installer lane and the drive's own serial hint, so `identifiers.stamped_lane` / `drive_guard.lane_verdict` say `ours`, `other` or `none`; `other` is refused before any other allowance, including for a drive the operator listed. `installed_drive_update` checks the same stamp after reading the target, and refuses any serial that is not this lane's own or enrolled.
- **`baseline/lib/cardinality.py`:** `exactly_one` / `at_most_one` raise an error that lists everything found; `survey` reads the attached disks, volume groups and logical volumes once (read-only) and reports how many Proxmox installs and Baseline drives there are and which volume group names are shared; `host_vg` resolves the volume group the RUNNING root lives in by its UUID (a bare `pve` can mean either drive) and can refuse when the name is shared. Used by the updater's drive lookup and the host installer's "other drive to protect" (two or more is refused). Not yet wired into every caller that defaults to `pve` (`drive_installer.DEFAULT_VG_NAME`, the web and control-panel defaults, `persist_bind_mounts`'s fallback): those are the next sites to move to `host_vg`.
- **Scrub.** Every real drive serial (PC601, PC401, a disposable test drive, and the serials of this machine's other drives) was removed from tracked code, tests, scripts and documents: synthetic `SYNTH...` serials in code and tests, descriptive placeholders in documents; test values derived from a real serial (identifiers' hex fragments, pinned host identifiers) were recomputed. Real MAC addresses in evidence files and tests, this development host's hostname, and an accidentally committed LibreOffice lock file were removed too. A hygiene test (`test_no_real_hardware_identifiers_in_tracked_files`) finds the serials on the machine it runs on (operator data and attached drives) and fails if any is in a tracked file, and checks that code has no serial-looking literal.
- Removed: `boot/prepare_scratch_drive.sh` (disabled since 2026-09-30, held a serial); `baseline-independent-drive-install` now takes its target from environment variables instead of constants.

## Not done, and why
- **Git history still holds the earlier values.** The repository was pushed before this; the serials, MACs and hostname are in earlier commits on GitHub. Removing them needs a history rewrite and force-push, which is the operator's decision (it breaks every other clone, including the parallel lane's); nothing was rewritten.
- Other environment-specific values remain in scripts and some evidence files: the local account name in `/run/media/<user>/...` build paths, private LAN addresses (`10.0.0.x`, `192.168.1.x`) in LAN-discovery evidence. They are not hardware identifiers; say if they should go too.
- The `INSTALLER_UUID` file (this lane's installer identity) is still in the repository: it names an installer lane, not a drive. Say if it should move to operator data as well.
