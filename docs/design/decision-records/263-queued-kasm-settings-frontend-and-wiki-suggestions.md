# 263 - Queued: a settings front end for Kasm, and a Wiki that turns logs into tested suggestions

Date: 2026-10-17. Status: QUEUED by the operator; nothing below is built. It builds on DR260 (the recipe, the settings catalogue, the telemetry and suggestions, the registry), which is built and verified.

## Operator request (2026-10-17), recorded as asked
1. "Baseline should have a low technical front end for Kasm Workspace settings as well as an advanced version that gives the full Kasm Workspace settings."
2. "It should have a Wiki folder made for that parses out concerns from the logs and has an intent to direct an AI to it to determine if there are any settings recommendations for the user, and that it would make a temporary build that it would either be able to do its own testing to see if it fixes the issues, or let the user try it out and see if it is an improvement, or put it in an archive for past suggested build changes."

## What already exists to build on (DR260)
- `kasm_settings.py`: the catalogue of all 87 settings from the release's own seed (name, category, title, type, default, secret or not, which services restart), typed override checking, secrets never set from a recipe. Settings are written the documented way (slip-stream) so Kasm encrypts them.
- `kasm_recipe.py`: components with states (required, used, unused), plugins, workspaces, settings overrides, registry; validated against the release's own compose file.
- `kasm_telemetry.py`: a history of memory, CPU and disk pressure, failing services, container restarts and memory kills, kernel driver errors, Kasm's own error lines (redacted, one fingerprint per repeating problem), the real values of setting changes (secrets only noted), and usage from Kasm's accounting; `suggestions()` turns that into items with evidence and benefit.
- `/workspaces` page; `baseline-kasm` commands; the VM's layers (persisted, plus a per-run session layer in reset mode), which are what make a temporary build cheap and safe: a trial is a reset-mode run or a separate dehydrated VM over the same base.

## Design sketch (not decided; for the operator to correct before any build)
**1. Two front ends over one model.** The catalogue already carries everything a form needs. *Simple*: a short list of plain-language choices (how long to keep logs, whether people can use clipboard or downloads, session time limits, how many sessions per person) each mapped to one or more settings with the reason and what it costs, a "what changes if I do this" line, and a note when a restart of a service is needed. *Advanced*: all 87 grouped by Kasm's own categories, searchable, typed inputs, secrets shown only as "set / not set", the services needing restart named, and every change recorded in the history with its real values. Both write the same way (the recipe's `settings`, applied by a rebuild or rehydrate; live changes only through Kasm's own admin API, which Kasm encrypts itself).
**2. A Wiki folder.** One plain-text page per recurring concern (a failing service, a repeating Kasm error, memory pressure, a kernel driver error ...), written from the history's fingerprints: what it is, how often and when, what it correlated with, which settings or sizes might matter, and what was tried. Plain files in a folder on APPDATA_ADMIN (readable by a person, by Baseline, and by an AI), regenerated from the history, never holding a secret (the history already redacts).
**3. An AI that reads the Wiki.** An intent (a written brief) points an AI harness at the Wiki and the settings catalogue and asks: given these concerns, are there settings or sizes worth changing, why, and what would you expect to improve. Its output is a *proposal* (settings to change, with the expected effect and how to tell it worked), never an applied change. Which harness is used is the operator's existing choice; credentials stay in the vault.
**4. A temporary build for each proposal.** The proposal becomes a candidate recipe (changed settings and sizes) built as a temporary VM over the same base (or a reset-mode run), kept apart from the real one, with its own data so it cannot touch the person's. Then one of three paths, the person's choice:
   - **Baseline tests it itself**: replays a defined check (the same probe, a scripted set of sessions, the metric the proposal said would improve) and records before and after.
   - **The person tries it**: opens the temporary build, uses it, and says better, worse or the same.
   - **Archived**: either way the proposal, its candidate recipe, the evidence, the test or the person's verdict, and what was decided go into an archive of past suggested build changes (also a folder of plain files), so the same idea is not proposed again unchanged and a good one can be promoted into the real recipe.
Nothing is promoted automatically: only the person promotes a candidate into the recipe.

## Questions to settle when this is picked up
Which settings belong in the simple view (I would propose starting from what the history shows people actually change). Which AI harness and how its cost is bounded. What counts as "fixed" for each kind of concern (the check each suggestion must name). How long a temporary build may live and how much space it may use (it is a layer, so it is small, but it needs a limit). Whether the archive is shared across hosts or stays per host.
