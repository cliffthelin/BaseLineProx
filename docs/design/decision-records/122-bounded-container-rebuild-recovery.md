# 122 — Application-owned bounded container rebuild recovery

Date: 2026-10-02
Status: implemented and verified for two actual native boundaries in disposable KVM; queue75 remains partial.

## Problem and behavior

DR121 recorded interrupted jobs but recovery after OS deletion still needed a
native shell. A missing CT could also make the container page fail to list the
remaining workloads. Baseline now journals a rebuild's base configuration and a
fresh random ownership marker before detaching/deleting its disposable OS.
Journal writes flush/fsync the file and parent directory. Clone creation carries
the marker in the native description; journal stages distinguish rebuilding,
cloning and configuring. This is a continuity check, not a new authorization or
cryptographic authenticity system.

Read-only inspection identifies either an absent native CT or this operation's
owned stopped partial clone. The application lists incomplete workloads without
claiming they are stopped/ready and offers **Recover rebuild** only for supported
state. Interrupted jobs still require Workload jobs inspection and exact-name
acknowledgement before a new recovery job; review is not success. Recovery itself
requires explicit confirmation and revalidates native state at execution.

Before recovery, retained paths must exist without symlink redirection, the
immutable base must match its recorded configuration, cluster-wide inventory
must succeed, and the selected ID must be vacant with no unregistered OS volumes,
or be a stopped LXC with the exact marker, expected hostname/root/mapping and
only expected retained mounts. Config errors never imply absence. Existing native
locks, running workloads, reused IDs, modified bases, extra mounts/disks and
orphan volumes are refused. Recovery never destroys a resource, unlocks a task
or deletes retained data. A missing OS is cloned; an owned partial clone is
configured in place. Native clone also refuses an occupied target ID.

Native inspection found template root names use `base-…`, and descriptions from
pct config end with escaped `%0A`. Fake fixtures were corrected, failing tests
confirmed, then implementation fixed. The stopped partial clone was preserved
through diagnosis and resumed without another clone/deletion.

## Evidence and limits

**2,882 guarded unit tests passed** (fake native runners plus actual loopback HTTP;
not hardware proof). Tests cover confirmed RED before GREEN, web confirmation,
missing-OS visibility, both recovery states, retained document, reused ID,
modified base, orphan volumes, failed inventory and unexpected mounts.

**Actual Proxmox-in-KVM proof**, `docs/verification/122`: on the already approved
disposable clone, test-only command interception paused (1) after actual detach
and OS deletion, before clone, then (2) after actual linked clone completion,
before configuration. Real service restarts recorded interrupted jobs. Both were
inspected, reviewed, recovered via authenticated application actions, and shut
down cleanly. `/home/job-proof` retained `job-retained-document`. A synthetic
stale reservation pointing to actual openSUSE base119 was refused; its native
configuration was unchanged. A final service restart retained recovery outcomes.
The removable test shim was removed; it is not a production recovery dependency.
These are interruptions at destructive workflow boundaries, not proof of killing
an in-flight native destroy/clone task or loss of host power.

No physical drive was written or freshly deployed. The running approved clone
retains its explicit read-only physical backing/writable qcow2 arrangement.
No operator credential was handled; root test login was freshly generated by
the established helper and supplied via stdin. Artifacts exclude credentials.
