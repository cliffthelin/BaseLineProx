# 267 - Ready-made operating system bases (the "custom builds" for the listed systems)

Date: 2026-10-17. Status: built and run here for Debian, Ubuntu, NixOS, CachyOS, Bazzite and Omarchy; FydeOS converted and measured but not usable as a plain VM; Qubes not built. NOT yet run on a real Proxmox host.

## Operator direction (2026-10-17)
"KASM still needs to build custom builds for Omarchy and other OSs still, and we need custom builds for Fyde and Qubes." Asked which was meant (ready-made VMs, Kasm desktop images, or both), the operator chose **ready-made VMs**. This is DR258's requirement ("every OS ISO the drive carries is spun up beforehand and configured with the default applications; the user's information is in the overlay; the base carries no credentials") made real, and the Kasm and queued work (DR266) is behind it.

## The design
- A **base** is built once, on the build machine (internet needed), by `baseline-build-os-base`: the system is installed unattended in QEMU from the image the installer already carries, with its desktop and the five applications where they exist, then made generic (no machine id, no host keys, no cloud-init state) and compressed to `<os>-base.qcow2` with `<os>-base.json` (its SHA-256, what was installed, what was checked, `holds_install_state_or_secrets: false`).
- The base holds **no account and no secret**. A VM made from it gets its own account from a seed at first boot (cloud-init's NoCloud `cidata` drive where the system has cloud-init; the system's own first-boot setup where it does not).
- A VM is made the way `ubuntu_environment` already makes one: the host's `create_overlay` (a disposable OS layer over the base, which is never written) plus a retained `baseline-home` disk for the person's files. **The account in the VM is the Proxmox user who is already signed in** (corrected 2026-10-17 after the operator pointed out that earlier versions gave each VM a login of its own with a one-time password): it carries that user's name, has no password at all, may use sudo without a prompt, is uid 1100 on every system (clear of the default users), and the console signs it straight in. The name is kept once in `owner.json` beside the retained disks so it persists until more Proxmox users are made. `prebuilt_environment.py` does this for every system; Proxmox's host class attaches the seed as a CD and the overlay as the disk through the code that already exists.
- `offline_cache.carry_os_bases` puts the bases into the installer's cache (`os-bases/`), refusing and reporting any base that does not match its own manifest or does not say it is free of secrets; `baseline-build-offline-cache --os-bases DIR` and `baseline-allscript-install --os-bases DIR` use it, and a cache with no bases is stale when bases are wanted. The launcher's "Available to create" tile shows **ready-made** for a system whose base is carried and creates it with `create_prebuilt` (no installer runs).
- The bases are never booted after they are generalized. Anything that needs a look inside is booted on a **throwaway layer** over the base (`inspect_overlay`, `boot_proof`, `first-boot`), which is deleted afterwards.

## What was done for each system, and what was proved

|---|---|---|---|

| Ubuntu 26.04 | The signed Ubuntu cloud image (signature and checksum verified) with the desktop installed by cloud-init | the same five | All five installed; desktop and agent present; **first boot account made** |
| NixOS 26.05 | The live ISO booted straight from its files and driven over its serial console: partition, then `nixos-install` from a generated configuration (labels not UUIDs, GRUB on the removable EFI path, cloud-init) | VS Code, Chrome, Spotify from nixpkgs; ChatGPT and Claude have no package and are recorded as needing a helper | Apps present; only system accounts; **first boot account made** |
| Bazzite | Anaconda with a kickstart appended to the ISO's initrd: the container image on the ISO, wipe the disk, no user, root locked | none yet (a helper is needed on an immutable system) | ostree deployment present, root locked, no human account, flatpak present, guest agent answers |
| Omarchy 4.0.4 | The ISO's own documented unattended path: a `cidata` drive with `user_configuration.json` (written from the configurator inside the carried ISO, schema 3.0.9), a `defer-provisioning` marker and unencrypted | none yet (helper) | Boots to Omarchy's own first-boot owner setup on a throwaway layer; no guest agent was reachable, so that is all that was checked |
| CachyOS 260809 | The live image's `cachyos-installer --config` headless mode (documented in its repository); it requires a user and passwords, so a throwaway user with random passwords is made and deleted afterwards and root locked | none yet (helper) | After the throwaway user was removed: no human account, root locked, cloud-init and the guest agent installed, an EFI fallback loader present; **first boot account made** |
| FydeOS 23 preview 2 | Not an installer: a VMware appliance. Its manifest is verified and the disk converted to qcow2 | none | Boots to its userland under QEMU (UEFI, SATA, e1000) but its desktop never starts: its kernel has no driver for any QEMU display (`frecon: No suitable drm driver found`, `i915.modeset=1` in its boot line). ## Problems found while doing it (each fixed)
- Debian's installer stalled in its own environment when it ran the application install (the base system and agent were fine); the same script runs correctly on the booted system, so applications are installed in a second boot through the guest agent. The apt "media failed" prompt came from a second optical drive; the payload is a virtio disk instead.
- The Debian answer file also needed the keyboard questions answered or the installer stopped on them.
- A guest that has not started its agent drops what is sent to it, so `sync` repeats until it answers (and gives up with a timeout), and a late answer to a repeated sync is no longer mistaken for the next call's reply.
- The agent runs with almost no PATH (NixOS especially) and, on Bazzite, under SELinux confinement: checks now put the usual directories on PATH, and the NixOS results first recorded as "missing" were wrong and were redone.
- CachyOS's installer unmounts the target before it runs the post-install script, so the script mounts the installed root and EFI partition itself.
- A stalled or failed build now kills its VM instead of leaving it running, and a stall guard stops an install whose disk stops growing for 20 minutes.

## Sizes (compressed, what the cache carries)
Debian 4.3 GB, Ubuntu 5.6 GB, NixOS 5.5 GB, CachyOS 3.8 GB, Omarchy 4.2 GB, Bazzite 7.6 GB: about 31 GB for the six that can be used as plain VMs (FydeOS's 3.8 GB is not offered), in addition to the 19 GB cache and the 16.6 GB Kasm base.

## Not verified, not done
- **Creating a VM from a base on a real Proxmox host** and starting it there. The unit tests use the host's fake and `prebuilt_environment`'s seed and overlay logic; the same bases were booted here under plain QEMU on a throwaway layer with a real seed (Debian, Ubuntu, NixOS, CachyOS).
- The application set on Bazzite, Omarchy, CachyOS and NixOS (ChatGPT, Claude): each needs a helper (Flatpak, the AUR or the system's own package set); the manifests list them as needing one rather than pretending.
- How Bazzite and Omarchy's own first-boot setups make the owner when started from the base (they were not driven).
- A Qubes kickstart and anything for FydeOS beyond what is above.
- Rebuilding the installer cache and ISO with these bases (the options exist; the cache build was not run).
- The CachyOS build ran its installer, then needed its post-install repeated by hand once because the first version of that script assumed the target was still mounted; the script was fixed and the result is what is recorded, but a clean end-to-end rerun of that one build has not been done.
- The throwaway account the CachyOS installer requires was verified gone only after the fact (the base's own check list shows it present before tidying, `checks_after_tidy` shows none).
