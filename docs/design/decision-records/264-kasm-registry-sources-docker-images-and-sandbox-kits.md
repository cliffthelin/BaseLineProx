# 264 - Workspaces from other registries (LinuxServer.io), Docker images in general, and Docker Sandbox kits

Date: 2026-10-17. Status: the import of named, reviewed workspaces from other Kasm registries is BUILT and checked against the real LinuxServer.io registry; the image mirror (Distribution) and anything for Docker Sandbox kits are INVESTIGATED, NOT BUILT, with the operator decisions they need listed at the end. Builds on DR260 (Baseline as a Kasm workspace registry).

## Operator request (2026-10-17)
Add LinuxServer.io to the registry the way Kasm usually does it; investigate adding Docker Hub "sbx_kit" results, or Docker containers in general, to the registry; consider how the Distribution registry, its manifest lists and similar systems do this.

## What was found (read from the live sources today, not recalled)
- **LinuxServer.io runs a Kasm registry: `https://kasmregistry.linuxserver.io/`** (schema 1.1: `versions.txt` offers `1.0` and `1.1`; `1.1/list.json`; icons under `1.1/icons/`). It is built from their public template (`github.com/linuxserver/kasm_workspaces_registry`, one folder per workspace with a `workspace.json` and an icon; a GitHub Actions build publishes it). It offers TWO workspaces today: Chromium and Firefox, image `lscr.io/linuxserver/chromium:kasm` and `.../firefox:kasm`, `docker_registry: https://ghcr.io/`, run configuration `entrypoint /kasminit`, `user 1000`, `HOME`, and `security_opt: seccomp=unconfined`; exec starts the browser on `$KASM_URL`.
- **Kasm documents adding a third-party registry as a UI step only** (Workspaces > Workspace Registry > Add new > paste the link). No documented API or configuration file adds one; the installer takes ONE default registry (`--default-registry-url`). So "add LinuxServer to the registry" has no scriptable documented form, and a person adding it by hand is the only documented way.
- **Their list covers Kasm 1.16.x, 1.17.x and 1.18.x, not 1.19.x** (this Kasm is 1.19.0). Kasm's docs do not state the matching rule. What was observed on the live 1.19 Kasm: it shows each workspace with only the compatibility entry for its own version, which suggests an entry with no 1.19.x is not offered. That was not proved by adding the registry (see "Not verified").
- **Kasm flags what can run commands**: `run_config` and `exec_config` "allow arbitrary commands to be run"; a workspace is marked orange for `user` not 1000 (`user_error`), privileged mode (`privilege`), or any property outside its ignored list (`flag_property`; `entrypoint` is on that list, `security_opt` is not). Kasm says many LinuxServer workspaces are flagged for exactly `seccomp=unconfined`, which "will significantly reduce" Kasm's protection.
- **The image is a multi-architecture OCI image index**, checked on ghcr.io with an anonymous token: `linuxserver/chromium:kasm` and `firefox:kasm` are `application/vnd.oci.image.index.v1+json` with linux/amd64 and linux/arm64 manifests PLUS two `unknown/unknown` manifests each (build provenance and SBOM attestations). That is the OCI form of the Docker "manifest list" (distribution spec, manifest v2.2 list); anything that copies these images must copy the whole index and every manifest it references, or the digest, the architecture choice and the attestations are lost.
- **Docker Hub `sbx_kit` ("Sandbox kit")** is a product type of **Docker Sandboxes**: 546 kits, all published by Docker (`docker.io/sbx/...`), either a *sandbox* (a whole agent environment) or a *mixin* (adds tools or configuration to one). A kit is a `spec.yaml` plus files to inject, stored as an OCI artifact and consumed by the `sbx` CLI (`sbx run claude --kit docker.io/sbx/<name>-kit:latest`; introduced in sbx 0.28; sources must be explicitly allowed from 0.34). Examples: coding agents (Claude, Codex, Crush, Kiro, Junie, Copilot), tools (mise, Neovim, Trivy, Task), `code-server-kit`, `playwright-kit`. Docker says the format and CLI are still changing.
- **Docker Hub images in general**: Kasm pulls whatever `docker_registry` and `image` a workspace names (Docker Hub is `https://index.docker.io/v1/`; private images take credentials). But a workspace's container must itself stream a desktop or app to Kasm's proxy (KasmVNC, built on Kasm's base images, entrypoint `/kasminit`); an ordinary container (a web service, a database) gives Kasm nothing to show.

## Compatibility verdicts
| Thing | Fits a Kasm workspace registry? | How |
|---|---|---|
| LinuxServer.io `:kasm` images (Chromium, Firefox) | Yes, they are built for it | Built here (below). 1.19 compatibility assumed and reported as unverified. |
| Other LinuxServer images (webtop and the like) | Not as they are | They serve their own web desktop on their own port with their own sign-in, not Kasm's session proxy. Only a `:kasm` tag is a Kasm workspace. |
| Any Docker Hub image built `FROM kasmweb/core-*` (Kasm's documented custom-image route) | Yes | A registry entry naming it. Baseline can build such a wrapper image around an app; not built. |
| A graphical app with no Kasm support | Only by wrapping it | Build a Kasm-based image that includes the app; Baseline-built, not built yet. |
| A non-graphical container (service, database) | No | Kasm has nothing to render. If wanted, that is a separate Baseline concept (a service container on Proxmox), not a registry entry. |
| Docker Sandbox kits (`sbx_kit`) | No | They are agent-environment recipes for Docker's microVM sandboxes, run by `sbx`, not container images with a desktop. They could be a future, separate kind of thing in Baseline (an agent sandbox VM) but nothing in them maps to a Kasm workspace field. Their trust model is also different: a kit can add credentials and network rules. |

## What was built
- **`kasm_sources.py`**: reads another registry's public `versions.txt` and `1.1/list.json` (https only, size limits, schema check, icons checked to be the image type their name says), keeps what the recipe names, and offers it through Baseline's own registry beside the carried workspaces. One address for Kasm to trust (the installer's single default registry), and a fixed, reviewed subset rather than "everything a registry ever adds".
- **Review is a hash, not a feeling.** Each included workspace is pinned to `reviewed`: a hash of its run configuration, exec configuration, image and image registry. If the upstream definition changes, it is left out and the build report shows the new hash and the definition to read; the recipe is updated only by a person. Any run-configuration property beyond `entrypoint`, `user` 1000 and `environment` is a finding and must be accepted by exact name (`run_config.security_opt`). LinuxServer's Chromium and Firefox were read today: the one accepted property is `security_opt` (`seccomp=unconfined`), the browser starts on the session URL, nothing else runs.
- **Compatibility is honest.** An entry with no entry for this Kasm's version is left out unless the recipe sets `assume_compatible_from` (here `1.18.x`); then it is included, shown as "not verified on this Kasm version" in the build output and on the Workspaces page, until it has been run on a 1.19 Kasm.
- **No internet at build time is survivable**: lists and icons are kept from the last build (`--sources-cache`); with neither, that source adds nothing and the report says why, and the rest of the build goes on.
- **Provenance is kept beside the registry, not in it**: `registry/sources.json` (every workspace asked for, included or not, with the reason, hash and definition). The Workspaces page shows it, including the definition to read for anything left out. Icons travel with the registry (`registry/1.1/icons/`) and are served beside the ones copied from Kasm.
- **Defaults**: the built-in and example recipes now enable Baseline's registry and take Chromium and Firefox from LinuxServer.io, named `Chromium (LinuxServer.io)` and `Firefox (LinuxServer.io)` so they never collide with Baseline's own Firefox. If the host has no bridge address to give Kasm, it simply uses Kasm's own default registry as before.
- **Not carried**: these images are pulled from `ghcr.io` when a session first starts, so they need internet. Chromium is about 1.25 GB.

## How Distribution and similar systems would do the offline part (investigated, not built)
Kasm's agent pulls with its own Docker daemon, so a workspace whose image is `lscr.io/linuxserver/chromium:kasm` fetches from the internet on first use. The usual answers elsewhere (Harbor proxy projects, Artifactory and Nexus remote repositories, Distribution's own pull-through cache) are: put a registry between the consumer and the source, keep the content addressed by digest, and rewrite image names to point at it.
- **Distribution (`registry`)** can run as a pull-through cache of ONE remote (`proxy.remoteurl`), as a plain registry, and in read-only mode (`maintenance.readonly.enabled`) from a read-only root directory. A Docker daemon's `registry-mirrors` applies to Docker Hub only, so for `ghcr.io`/`lscr.io` images the registry list must name the mirror's address in `image` and `docker_registry` (a rewrite in the list Baseline already generates).
- **Copying must keep the index**: use a copier that preserves the whole OCI index and all referenced manifests (`skopeo copy --all`, `crane copy`), so the digest, both architectures and the attestations survive, and pin by digest (`image@sha256:...`), because `:kasm` is a moving tag.
- **Fit with Baseline's storage rules**: the images are vanilla and content-addressed, so they can live on INSTALLER_CACHE (read-only, nothing private), served by a read-only Distribution; nothing user-specific is ever pushed there. Pulls from a plain-HTTP mirror need the mirror address in the Kasm VM's Docker `insecure-registries` (or TLS), a change inside the VM.
- Cost to consider: Chromium plus Firefox is roughly 2.5 GB per architecture before layers shared with Kasm's own base are counted.

## Decisions for the operator
1. Build the mirror (Distribution, read-only on INSTALLER_CACHE, images pinned by digest and carried into the installer) so these workspaces work with no internet, or keep them pulled on demand?
2. Where does the mirror run (on the Proxmox host, in the Kasm VM, or in its own small VM), and plain HTTP with `insecure-registries` or TLS?
3. Do you want Baseline to build Kasm-based wrapper images for apps that have no Kasm workspace (the documented custom-image route)?
4. Docker Sandbox kits: leave out of Kasm; record as a possible separate "agent sandbox" feature only if you want that.
5. Adding the LinuxServer registry by hand in Kasm's own UI remains possible; its address is `https://kasmregistry.linuxserver.io/`. Baseline's route (reviewed subset, one address) was chosen here; say so if you would rather have Kasm point at theirs directly.

## Operator answers and recommendations (2026-10-17, after the above)
**Operator**: asked how much space the mirror needs; suggested it could be read from a local drive or hosted on the network by a file server and asked for a recommendation; said Kasm is not meant to be limited to its verified library (the reason for sharing the registry material), that wrapper images for apps without a Kasm workspace are wanted (decision 3: yes), that if there is no clear reason for Baseline to run its own registry now it can be built in later, and asked whether Baseline's registry could be improved or replaced by an open, battle-tested one such as Distribution.

**Space** (measured on ghcr.io today from the real manifests; a registry stores layers compressed, as pushed):
| What | Compressed, in the mirror |
|---|---|
| Chromium `:kasm`, linux/amd64 | 1,062 MB |
| Firefox `:kasm`, linux/amd64 | 1,027 MB (no layer is shared with Chromium: 28 layers, 28 distinct) |
| Both, amd64 only | about 2.1 GB |
| Their build attestations (provenance, SBOM) | about 0.1 GB |
| Both, amd64 and arm64 | about 4.1 GB, 4.3 GB with attestations |
| Each further browser of this kind | about 1 GB |
Registry bookkeeping is a few KB per image. Building it by copying straight from the source into a temporary registry needs no extra scratch; staging an OCI layout first needs about the same again while building. For scale: the carried Kasm base is 16.6 GB, so amd64-only is about 13% more; inside the Kasm VM Docker keeps the images uncompressed, so using both takes about 2.5 GB of the VM's 20 GB admin disk (1,250 and 1,230 MB by the registry's own figures). Every host here is amd64; arm64 is only worth carrying for an arm machine.

**Where it is served from** (Docker cannot pull from a drive or a file share; it needs a registry API, or images loaded into it):
- A. Load the images into the Kasm VM's base (no server, fully offline, but a copy inside every base, and every added workspace means rebuilding a 16 GB base, which is the opposite of "not limited to a verified library").
- B. **A read-only Distribution on the Proxmox host serving from a read-only drive (INSTALLER_CACHE), listening on the VM bridge only. Recommended.** One copy; adding a workspace adds blobs, not a rebuild; it needs only the mirror address in the Kasm VM's Docker `insecure-registries` (or TLS), and nothing private is ever on that drive.
- C. A network file server: a share is only somewhere to keep B's storage. To share one mirror across several Baseline hosts, run B on one host or on the file server and let the others pull over the LAN, with TLS and credentials because it is then exposed beyond the bridge. Because image names are rewritten from one setting, moving B to the network later is a one-address change.

**Replacing Baseline's registry with Distribution**: they are two different layers. Distribution is an OCI/Docker IMAGE registry (blobs and manifests). What Kasm calls a workspace registry is a static JSON catalogue (`versions.txt`, `1.1/list.json`, icons), which Kasm's own and LinuxServer's are plain static sites (LinuxServer generates theirs from a public template and hosts it on GitHub Pages). Distribution cannot serve the catalogue and the catalogue cannot serve images. So: images, when the mirror is built, should be a battle-tested Distribution (not something of Baseline's own); the catalogue should stay a few static files. Baseline's route for them is small and verified, but it is one of the few unauthenticated exceptions in an authenticated web app. Recommendation: keep it as it is now (no clear reason to change it yet), and when the mirror is built serve the catalogue from the same small read-only service that fronts Distribution, so Baseline's own web app has no public routes at all. Until then the catalogue generator is the only part that is Baseline-specific, and it stays small enough to replace with LinuxServer's template if that is ever preferred.

**Decided / deferred**: wrapper images for apps with no Kasm workspace: wanted, to be built later. The mirror: not built now; build it when an imported or wrapper workspace is needed on a machine without internet, or when the first wrapper image exists. Docker Sandbox kits: left out.
