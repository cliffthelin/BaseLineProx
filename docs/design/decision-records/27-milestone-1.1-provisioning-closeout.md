## The fix: `boot/provision.sh` no longer touches its own execution context

Decision record 26 found the defect directly: the old script called `systemctl disable --now getty@tty1.service` then `systemctl enable --now baseline.service`, both of which disrupt the live tty1 session the script itself might be running from — confirmed by `provision.log` stopping execution immediately after the `getty@tty1.service` removal line.

Fixed (commit `0d7e900`, prior to this session's continuation) by staging all files first (unchanged), then running atomic verification (`[ -s "$f" ]` for every staged file, `[ -x "$f" ]` for every entry point, unit-file presence checks) via a `verify_fail()` helper that aborts with `exit 1` on any failure, then `systemctl enable` (no `--now`) all three units with **zero** direct `getty@tty1` manipulation — relying entirely on `baseline-firstboot.service`'s own `Conflicts=getty@tty1.service` / `Before=baseline.service` ordering to take over tty1 safely at the *next* boot, which is systemd's job, not the script's. A final verification loop confirms `systemctl is-enabled` reports `enabled` for all three units before the script prints success.

## State-model correction: `network_repaired` must mean success

While reviewing the first crash-recovery attempt (below), it became clear the journal was recording `{"state": "network_repaired", "network_ok": false}` whenever the repair pipeline's own safety check refused to touch an already-healthy interface, or apply/verify otherwise failed. A state named "repaired" that can also mean "not repaired" is exactly the kind of ambiguity that makes recovery logic and audit history hard to reason about correctly — precisely what happened here.

Fixed in `baseline/lib/firstboot_statemachine.py` (commit `b3070b0`): the single `network_repaired` state was split into two distinct terminal states — `network_repaired` (entered if and only if the repair applied and verified, or the lifeline was already healthy) and a new `network_repair_failed` (entered for any refused or failed outcome). `record_transition()` now enforces this as a hard invariant, not just a convention: calling it with `state="network_repaired"` and `network_ok=False` raises `ValueError` directly. Recovery now branches on which of the two states was actually recorded, never by inferring success from a shared phase name. Added: a direct test that the invariant guard raises, an end-to-end test that no failure-inducing scenario in the suite ever produces `network_repaired` with `network_ok: false`, and a new `test_resumes_from_network_repair_failed_state_without_retrying` test mirroring the existing `network_repaired`-resume test for the failure path. 22/22 `firstboot_statemachine` tests pass, 208/208 full unit suite passes.

## Fresh proof 2 (failure-state recovery only — see correction above): interruption after confirmation, before commitment (`experiments/m1-1-2-crash/`)

**This test's result is real and is kept as evidence, but it demonstrates less than it first appeared to.** It was run before the state-model correction above, and its own methodology (see below) meant the "repair" it interrupted was actually a *refused* repair, not a successful one — so what it actually proves is fail-closed recovery from a recorded failure, not the successful-mid-flight-continuation scenario that was actually requested. That scenario is proven separately in "Fresh proof 3" below, from an uncontaminated run. This section is preserved exactly as originally written, not edited to look like it tested something it didn't.

A second, completely independent fresh disposable install (`fqdn=baseline-crash.local`), provisioned unattended the same way, confirmed via the same `PASS`/`PASS` log lines.

**Method**: rather than trying to time an external kill against an unpredictable network round-trip, a small watcher script (`killwatch.sh`, test-harness-only, never part of the shipped system) was fetched onto tty2 and polls `/var/lib/baseline-firstboot/journal.json` every 0.15s; the instant its last recorded state becomes `network_repaired`, it sends `pkill -9 -f baseline-firstboot` and exits. This was pre-authenticated and pre-staged on tty2 before CONFIRM was sent on tty1, so the watcher was already polling when the real CONFIRM keystroke went in.

**What happened**: the watcher fired and printed `KILLED_AT_STATE=network_repaired`. Inspection immediately after showed:

- The journal's last transition was `network_repaired` with `network_ok: false` — because a manual `dhclient vmbr0` run on tty2 (needed only to give that shell's `curl` fetch of `killwatch.sh` an IPv4 route — a side effect of this test's own methodology, not a defect) had already brought the interface up before the repair pipeline's own apply step ran, so its safety check correctly refused to touch an interface that was reporting `address_assigned/gateway_reachable OK` ("refusing to change a device that isn't actually broken"). This is a genuine, correct safety behavior of the repair pipeline, not a bug — but it means this run demonstrates recovery from an interrupted **network-refusal** decision rather than an interrupted **package install**, which is still squarely "after confirmation, before commitment" and is reported here honestly rather than reframed as the originally-intended scenario.
- No completion marker existed. `systemctl status baseline-firstboot.service` showed `Active: failed (Result: exit-code)`.
- `baseline-firstboot.service`'s own process was gone (killed), confirming the interruption was real, not merely a slow poll catching a normal transition.

**Reboot, then recovery verification**:

- `diff` between the journal captured immediately before reboot and the journal read immediately after reboot produced **zero output** — byte-identical. The resumed run did not re-run network diagnosis or re-apply any change; it read the already-recorded `network_repaired`/`network_ok: false` state and reached its `network_failed` conclusion without writing anything new.
- `systemctl status baseline-firstboot.service` showed a **new** invocation for this boot (new invocation ID, new timestamp), `Active: failed (Result: exit-code)` again, but **CPU: 45ms** — against **668ms** for the original run that actually performed discovery, diagnosis, and repair. The ~15x reduction is corroborating evidence the expensive already-completed work was not repeated.
- No completion marker exists after the second boot either — package installation correctly never ran.
- **Decisive package-state check**: `iperf3` — which nothing else in a stock Proxmox install depends on or pulls in — is confirmed `dpkg -s`: *"package 'iperf3' is not installed and no information is available"*. (`smartmontools`, `ethtool`, and `lm-sensors` are present, but as Proxmox's own base dependencies — `lm-sensors` is marked `[installed,automatic]`, i.e. pulled in as *someone else's* dependency, not requested by this pipeline.) Since the five-package install is one atomic `apt-get install` call, `iperf3`'s absence is conclusive proof the install step never executed on either boot.
- Baseline's own console app took over tty1 as normal fallback behavior (`Before=baseline.service` ordering runs regardless of `baseline-firstboot.service`'s exit status), correctly and honestly reporting `BaselineOS — offline - stopped at address_assigned` — an accurate reflection of the actual (test-induced) network state, not a false "healthy" claim.

This is real, valid evidence of fail-closed recovery: a real kill of the real process, after a real durable journal write, with recovery proven by (a) an unchanged journal, (b) a near-zero-cost resumed run, (c) no re-attempted or skipped authorization, and (d) definitive package-state evidence that nothing already-decided was redone. What it does **not** prove is continuation after a *successful* repair — see Fresh proof 3.

## Fresh proof 3: successful mid-flight continuation — the scenario actually requested (`experiments/m1-1-3-midflight/`)

A third, completely independent fresh disposable install (`fqdn=baseline-midflight.local`), provisioned unattended the same way, confirmed via the same two `PASS` log lines.

**Corrected method — nothing touches the network after the fixture boot begins.** The contamination in fresh proof 2 came from running `dhclient` on tty2 *after* rebooting into the broken-network fixture, to give that shell's own `curl` fetch a route. This pass eliminates that entirely: the watcher script (`killwatch.sh` — same test-harness-only tool, unchanged logic, now polling for `network_repaired` which is structurally success-only after the fix above) was delivered **together with** the main payload during the earlier pre-authorization provisioning boot (the same boot where `provision.sh` itself runs, which already legitimately uses the network to fetch code) and staged at `/root/killwatch.sh` on disk *before* the reboot into the fixture. After that reboot, tty2 was used only to log in and run the already-present script — no `curl`, no `dhclient`, no network activity of any kind during the authorization wait or the repair itself.

**What happened**: CONFIRM was sent on tty1 with the watcher already polling on tty2. It fired within seconds, printing `KILLED_AT_STATE=network_repaired`. Inspection immediately after showed:

- The journal's last entry was `{"state": "network_repaired", "network_detail": "vmbr0 gained a new inet dhcp stanza (existing inet6 stanza preserved); address=10.0.2.15 gateway=10.0.2.2"}` — a **genuine applied repair**, not the "already healthy, refusing to touch it" artifact from fresh proof 2. No `network_ok` field at all, matching the corrected schema (success is now implied by the state itself, not a flag that could be wrong).
- No completion marker existed. `systemctl status baseline-firstboot.service` showed `Process: ... (code=killed, signal=KILL)` — a real `SIGKILL`, not a graceful exit.
- The journal was copied to `/root/journal_before_reboot.json` before doing anything else, for an exact before/after comparison.

**Reboot, then continuation verification**:

- `diff` between the pre-reboot and post-reboot journals showed **only additions** — every changed line was prefixed `>` (added), none `<` (removed/changed). `packages_installed`, `packages_verified`, and `committed` entries were appended; the `network_repaired` entry and everything before it was untouched.
- `grep -c '"network_repaired"' journal.json` on the final journal returned **1** — no second/duplicate `network_repaired` entry was ever written, confirming the repair transaction itself was not re-run on resume.
- `systemctl status baseline-firstboot.service` for the resumed boot's invocation showed `Process: ... (code=exited, status=0/SUCCESS)` and `CPU: 2.994s` — a real, successful run that did real work (package installation, including creating the `iperf3` system user/group), not a short-circuit.
- The completion marker now exists (`2026-09-24T11:28:19`); the journal's final state is `committed`.
- **Independently verified**: all five packages `dpkg -s` = `install ok installed` (including `iperf3`, confirmed genuinely installed this time — the opposite of fresh proof 2's decisive absence check, exactly as expected once the repair actually succeeds); `iperf3` confirmed `disabled`/`inactive`/not listening on `:5201`; `vmbr0` still shows `10.0.2.15/24` — the same address recorded at repair time, not reapplied or changed.
- **Second reboot, non-repetition**: tty1 showed Baseline's TUI directly (`BaselineOS — online - lifeline up`), no first-boot screen. Via tty2: completion-marker timestamp unchanged, a **new** `baseline-firstboot.service` invocation ran this boot but exited in **39ms** (against the 2.994s real run) — the already-completed short-circuit, not a redo.

This is the scenario the Milestone 1.1 correction actually asked for: **a successful network repair is durably recorded, the process dies, and the next boot continues with package installation and reaches commitment without repeating the repair** — proven directly, not inferred, from an uncontaminated run.

## Addendum (2026-09-24): `network_repaired` tightened to require explicit positive verification, before physical deployment

Reviewing the corrected evidence above surfaced one more small gap: the invariant guard only refused an *explicit* `network_ok=False`. A caller that simply omitted the field, or passed `None`/a truthy-but-wrong value, could still have written `network_repaired` with no genuine proof anything was checked - functionally safe today (production code always passes it explicitly), but not structurally guaranteed the way it should be before a real physical drive is in play.

Tightened `record_transition`'s guard (commit `d03d5d3`) to require **all** of: `network_ok is True` (exactly, not merely not-`False`), a non-empty `target_interface`, and a non-empty `verification` dict whose every value is exactly `True`. The evidence is real, not fabricated: `RepairResult` (`repair.py`) gained a `verification` field populated only on genuine success (`address`/`gateway` for replace-mode; `address`/`gateway`/`dns`/`https` for additive-mode, the latter two true by construction since `verify_target_extended` only returns `ok=True` after both pass); the already-healthy fast path reuses `discover()`'s own address/gateway facts via a new `firstboot_network_repair.facts_verification()` helper rather than inventing anything. 7 new tests cover every combination of omitted/`None`/truthy-wrong `network_ok`, missing/empty `target_interface`, and omitted/`None`/empty/non-dict/malformed-value `verification`, plus two end-to-end checks proving the real production path (not just hand-constructed fixtures) supplies valid evidence on both the repaired and already-healthy branches. 215/215 full suite passes. Unit/full-suite validation only, per instruction - no QEMU rerun, since the underlying repair/verification behavior was not changed, only the journal's write-time invariant around it.

## What this means for Milestone 1

The gap decision record 26 identified — "provisioner partially runs → operator repairs → reboot → integrated workflow succeeds" instead of "provisioner runs unattended to completion → reboot → integrated workflow succeeds" — is closed: this pass demonstrated exactly the latter, from completely fresh images, with no manual completion steps. The crash-recovery claim now rests on solid ground in all three shapes that matter: normal success, recovery from a recorded failure, and — the scenario that was actually missing — recovery that continues on to complete an already-successfully-repaired boot. Combined, Milestone 1's original goal — a reproducible, unattended Proxmox-substrate path back to the original Baseline functionality, that survives a real mid-flight interruption in either direction — is functionally complete in the disposable-QEMU reference environment. Physical-hardware deployment (the item explicitly listed above as unverified) remains the next validation step before any real installation, not a reason to discount this milestone. GUI/browser sandbox work, the Proxmox capability adapter, and any physical-drive work remain deferred to a future milestone and were not started in this pass.
